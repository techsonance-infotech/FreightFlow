3. Multi-Tenancy, Licensing & Module Control Architecture
3.1 Multi-Tenancy Model
FreightFlow Pro uses a Schema-per-Tenant model within Supabase PostgreSQL, enforced via Row-Level Security (RLS) policies. Each tenant (transport company) gets:
A unique tenant_id (UUID) stored on every table
RLS policies that automatically filter all queries by tenant_id extracted from the JWT
Shared application servers — tenant isolation is at the database row level
Option to upgrade to dedicated Supabase project for enterprise clients (data isolation)

3.4 Licensing Engine
FreightFlow Pro is sold as a time-based SaaS license. The licensing engine manages:
Feature
Implementation
License Key Generation
Cryptographically signed JWT containing: tenant_id, plan, expiry_date, max_users, max_vehicles, enabled_modules
License Validation
Backend middleware validates license JWT on every API request; rejects if expired or tampered
Expiry Handling
30-day, 7-day, 3-day, 1-day email + in-app warnings before expiry; grace period of 7 days post-expiry (read-only mode)
License Renewal
Admin pays → webhook triggers license extension → new JWT issued; no service interruption
License Plans
Starter (1 company, 5 users, 20 vehicles) | Growth (3 companies, 25 users, 100 vehicles) | Enterprise (unlimited)
Usage Metering
Vehicle count, user count, monthly LR count tracked and compared against plan limits in real-time
Violation Handling
Soft block on new record creation if over limit; hard block if license expired > 7 days
Offline Grace
License cached locally for 24 hours; allows offline use with re-validation on next connect

4.6 Row-Level Security Policy Pattern
All tenant tables have the following RLS policy applied automatically during schema migration:
Policy
SQL Pattern
SELECT
USING (tenant_id = (SELECT tenant_id FROM users WHERE auth_uid = auth.uid()))
INSERT
WITH CHECK (tenant_id = (SELECT tenant_id FROM users WHERE auth_uid = auth.uid()))
UPDATE
USING (tenant_id = ...) WITH CHECK (tenant_id = ...)
DELETE
USING (tenant_id = ... AND deleted_by = auth.uid())

11. Coding Conventions & Standards for AI Agents
11.1 File & Folder Naming
Pages: kebab-case — /app/lr-management/page.tsx
Components: PascalCase — LRCreateForm.tsx, DealerSelectModal.tsx
Utilities: camelCase — formatCurrency.ts, calculateGST.ts
Types: PascalCase with T prefix — TOrder, TDealer, TEmployee
API routes: kebab-case — /api/v1/lorry-receipts, /api/v1/fleet/vehicles
DB tables: snake_case — lorry_receipts, order_details, freight_invoices

11.2 Currency Handling
All amounts stored as INTEGER (paise) in DB — never float — to avoid floating point errors
Display as rupees: amount / 100, formatted with Intl.NumberFormat('en-IN', {style: 'currency', currency: 'INR'})
Input as rupees: multiply by 100 before storing

11.3 Date Handling
All dates stored as ISO 8601 UTC in DB
Display in IST (Indian Standard Time) using date-fns-tz with 'Asia/Kolkata' timezone
Date format for display: DD/MM/YYYY — Indian standard

11.4 Error Handling
All API errors return { error: string, code: string, details?: any } with appropriate HTTP status
Frontend: React Error Boundaries for component crashes; toast notifications for API errors
All errors logged to Sentry with tenant_id (no PII in Sentry)

11.5 Testing Requirements
Unit test every financial calculation function (GST, TDS, payroll, freight total)
Integration test every API route with real Supabase test project
E2E test the 5 critical paths: Create LR, Generate Invoice, Receive Payment, Process Payroll, File GSTR-1
All tests must pass before merging to main branch
